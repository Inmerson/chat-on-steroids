## Approaches considered

### 1. Selective capability port — chosen

Audit every upstream 2.0.9 capability against the current fork, then re-derive the missing behavior in the fork's current subsystem boundaries.

Advantages:

- preserves Persistent Core, Agent System 3.0, Control Center, durable execution, multi-device routing, the completed Plugins platform, browser/model discovery, and the current permission model;
- avoids reintroducing upstream structures that the fork has already superseded;
- lets each trust-boundary change receive targeted regression tests;
- avoids duplicate implementations.

Cost: more engineering work than cherry-picking because overlapping features must be reconciled semantically.

### 2. Cherry-pick the 2.0.9 feature commit

Cherry-pick `c6f2014` and then the three follow-up commits.

Rejected because the feature commit changes roughly two hundred files and assumes upstream ownership of MCP surfaces, session orchestration, renderer layout, desktop tooling, and agent behavior. The fork has independently evolved those same areas.

### 3. Keep upstream modules beside fork modules

Copy 2.0.9 implementations into parallel files and route selected calls to them.

Rejected because it creates duplicate authority for MCP tools, desktop control, agent/session state, and renderer surfaces. It also conflicts with the requirement that the project contain no duplicate implementation copies.

## Classification rule

Every upstream hunk is classified before porting:

- **ALREADY_PRESENT** — the current fork already implements the behavior, possibly through different code.
- **PORT** — the capability is useful and missing; re-derive it in current fork architecture.
- **SUPERSEDED_BY_FORK** — the upstream solution targets an older architecture and must not be imported.
- **EXCLUDE** — not required for this product, duplicates an intentional fork decision, or would weaken an existing boundary.

Tests and implementation evidence decide the classification; filenames alone do not.

## Capability group A — Code Mode, plans, and model-facing coding behavior

Port the 2.0.9 Code Mode concept as a bounded composition layer over the current MCP registrations.

Required behavior:

- add an isolated JavaScript `exec` composition surface only where it does not collide with an existing direct tool name;
- nested calls must run through the current live permission, caller identity, workspace, recording, and tool guards;
- no Node.js, filesystem, network, imports, timers, or persistent global state inside the Code Mode runtime;
- enforce explicit source, memory, CPU, wall-clock, nested-call, concurrency, image, and output bounds;
- preserve direct individual tools for simple calls and for operations whose native file arguments or continuation semantics do not fit Code Mode;
- lifecycle/finish operations remain direct calls rather than nested Code Mode actions;
- plugin Code Mode must compose only tools the plugin surface currently exposes; it must not inherit Core filesystem permissions.

Port the saved plan/agent-plan capability into the current execution and orchestration model rather than creating a second planner authority.

- plans are durable user-visible execution artifacts;
- Agent System 3.0 Manager/DAG remains authoritative for orchestration;
- a plan must never silently replace an already approved durable execution plan;
- plan UI must integrate with the current workspace instead of adding a duplicate upstream agent pane.

Port the useful Codex-derived coding instructions, adapted to current Chat On Steroids tools and permission semantics. Any copied/adapted Codex text or code must retain the required Apache-2.0 notices and provenance files.

Port automatic background command-result delivery only through the current `exec_command` / `write_stdin` ownership model. Results must remain bound to the authenticated caller/session and must not bypass terminal continuation rules.

## Capability group B — Windows Computer Use overhaul

Port the redesigned Windows desktop control behavior into the existing `computer/*` subsystem and Desktop connector.

Target capabilities include:

- stronger native window identity, including process/app identity where Windows exposes it;
- installed-app discovery and launch by trusted OS-derived app identity;
- richer UI Automation actions and accessibility context;
- exact window-scoped input targeting;
- safer paste semantics with target activation and explicit uncertainty if delivery cannot be proved;
- improved popup/owned-window handling;
- capture of related owned windows where useful;
- improved frame-to-image coordinate mapping;
- native window capture improvements;
- clearer partial-action and capture-after-action failure semantics;
- support for drag duration, click count, native wheel semantics, and explicit UI actions where the OS supports them.

Non-negotiable invariants:

- screenshot frame identity remains authoritative for coordinate actions;
- stale frame/ref/helper generations fail closed;
- physical input cannot silently retarget another window;
- permissions continue to be enforced by the Desktop connector and current capability gates;
- Windows-only capabilities must not leak into macOS/Linux live discovery;
- the desktop helper lifecycle remains generation-scoped and teardown-safe.

The upstream desktop implementation may be used as a reference, but the port must preserve the fork's current helper/process ownership and packaging model.

Upstream `tools-desktop-macos.ts` and its macOS Desktop-specific behavior are explicitly outside this port. The fork currently masks Desktop capabilities outside Windows in `platform.ts`; changing that platform policy would be a separate architectural task.

## Capability group C — browser bridge, message delivery, sessions, and recovery

Port missing 2.0.9 reliability changes after checking them against current 2.2.0 fixes.

The audit must explicitly cover:

- exact request/send evidence when a native reply arrives before page instrumentation settles;
- fetch instrumentation preserving exact request identity;
- Markdown/native receipt observation used by the content-script tests;
- worker reuse and idle-tab handling;
- workflow retry semantics;
- Compact & Resume transaction reliability;
- recorder attribution repair and final-message identity;
- background/content/Fiber coordination during reload/navigation;
- message delivery that does not duplicate already accepted work.

Fork invariants take precedence:

- exact conversation ownership and navigation epoch remain required;
- Persistent Core and the browser bridge remain separate lifecycles;
- worker chats continue to obey Agent System 3.0/fork broker ownership;
- durable execution rollover remains Core-owned;
- the current 2.2.0 tunnel/recovery hardening remains authoritative;
- already-ported later upstream fixes are classified ALREADY_PRESENT rather than reintroduced.

## Capability group D — workspace UI, i18n, transcript navigation, and connector refresh

Port Simplified Chinese support using one translation layer and one locale catalog.

- English remains the source locale;
- `zh-CN` is the first translated locale;
- strings must be keyed through a central i18n helper instead of duplicated component-specific maps;
- the existing 2.2.0 workspace shell, sidebar, Plugins workspace, Control Center, Fleet/Devices, Core Health, browser/model controls, and session views remain the layout authority.

Do not port the upstream local Projects catalog/sidebar grouping. The current `workspace.ts` contract intentionally learns a cwd from exact-chat file use, has no workspace id or user/model setter, and moves that learned workspace transactionally across worker/resume identities. A durable local Project catalog would create a second workspace authority and conflicts with that invariant.

Port the missing transcript navigation behavior into the existing session viewer instead:

- the default detail request remains a bounded newest tail;
- the user can page backward into older durable events without loading the full transcript;
- the user can move forward again and return to the live tail with a clear “Back to latest” control;
- older/newer requests are fenced by the current selected-session/load generation so a late historical page cannot overwrite another selected chat;
- live refreshes do not evict the historical window while the user is reading it;
- renderer row/text budgets remain bounded.

ChatGPT's own Project route identity (`/g/g-p-…`) is a separate browser-placement concern. If the browser hunk audit proves the current fork lacks useful Compact & Resume Project affinity, it may be ported as exact continuation metadata only. It must never grant or select a local filesystem workspace.

Port the connector-refresh reminder so an app/extension update can tell the user when ChatGPT connector metadata should be refreshed. This reminder must be informational and must not mutate connector configuration without user action.

Keep the current bounded/sanitized tool-result renderer as authority. Only its app-authored labels participate in the new i18n layer unless a focused regression proves a distinct 2.0.9 presentation behavior is still missing.

## Capability group E — recorder performance, durability, and presentation

Audit and port the 2.0.9 recorder/store improvements that materially reduce unnecessary work or make final message identity more reliable.

Candidate areas include:

- bounded canonical message storage and replacement;
- faster recording paths that avoid rewriting or reparsing unrelated history;
- session prompt/title helpers where they improve current behavior without creating a second source of truth; the audit has already confirmed title provenance is only partial in 2.2.0, so the bounded `fallback | provider | manual` title authority is a PORT item;
- logger redaction and bounded operational output;
- transcript folding/order fixes;
- clearer command-batch/process result presentation.

Current fork session IDs, conversation lineage, handoff/continuation transactions, token-pressure presentation, and durable catalog semantics remain authoritative.

## Capability group F — legal, notices, packaging, and release metadata

No public version bump, tag, installer publication, or release is part of this implementation task. Release preparation is a separate verified step after the port is complete.

## Implementation sequencing

The port should be built in dependency order so each stage remains independently testable:

1. legal/provenance scaffolding needed by copied Codex-derived material;
2. common MCP declaration/composition primitives;
3. Code Mode runtime and direct-surface integration;
4. plan/agent-plan integration with existing durable execution/orchestration;
5. background command-result delivery;
6. Windows Computer Use overhaul;
7. browser/extension evidence and recovery changes;
8. recorder/session performance and identity changes;
9. i18n, project/transcript controls, connector-refresh reminder, and tool-result UX;
10. cross-subsystem verification and packaging smoke.

Independent groups may be developed in isolated worktrees/workers, but the prime branch owns final integration and verification.

## Testing strategy

Production changes use targeted regression-first development where behavior can be expressed deterministically.

Each capability group must have its own focused tests before full-suite verification. The expected test families include:

- `code-mode-*`, MCP declarations, inbound identity, kernel/tool surface tests;
- plan/agent-plan and durable execution/orchestration tests;
- command-batch, exec notices/result delivery, unified exec parity;
- Windows API/apps/capture/keys/accessibility/input/focus/helper-generation tests;
- bridge, content-script, extension, Fiber, correlation, continuation/resume, agents;
- recorder/session/backend-recording/attribution/final-identity/timeline tests;
- renderer i18n/layout/state/tool-result/plugin-refresh/project controls;
- third-party notice/license verification.

After focused tests pass, run the exact protected verification gate, then build/package checks appropriate to the changed surfaces.

For Windows Computer Use and browser races, unit tests are not sufficient by themselves. Use a live packaged smoke or deterministic native fixture for behaviors whose correctness depends on real UI Automation, capture, focus, Electron, or ChatGPT-page ordering.

## Acceptance criteria

The port is ready for release preparation only when all of the following are true:

- the authoritative project exists only at the Project Inmersion path;
- every upstream 2.0.9 capability is explicitly classified;
- all PORT items are implemented through current fork-owned boundaries;
- no duplicate upstream/fork authority exists for MCP tools, plans, agents, sessions, desktop control, or renderer surfaces;
- existing 2.2.0 features remain present: Persistent Core, Agent System 3.0, Control Center, durable execution and rollover, Infinite Loop/scoped recovery, multi-device, Plugins, browser/model discovery, attachment/artifact safety, tunnel hardening;
- direct and negative trust-boundary tests pass;
- exact protected verification passes;
- build/package smoke passes for affected targets;
- companion extension and app protocol/version metadata remain internally consistent;
- legal/NOTICE inventory covers every retained third-party source;
- no tag or public release is created until the separate signing/release gate is satisfied.

## Explicit exclusions

This work does not:

- merge or rebase the fork onto upstream;
- replace Agent System 3.0 Manager authority with upstream plan UI logic;
- replace current Plugins with an upstream duplicate plugin architecture;
- restore the upstream heuristic provider-cost estimator as authoritative billing data;
- weaken approved-root, caller/conversation, desktop-window, extension-protocol, or Windows signing gates;
- keep a second physical project copy after migration;
- publish a release.
